# DATA_MODEL — Pokemon TCG Tracker

The full, authoritative description of the IndexedDB schema, the TypeScript types it produces, and the principles that protect user data.

---

## 1. Storage layer

- Database engine: IndexedDB
- Wrapper: [Dexie](https://dexie.org/)
- Database name: `pokemon-tcg-tracker`
- Versioned via Dexie's `version().stores().upgrade()` chain. Each version increment is a real migration with a test in `tests/migrations.test.ts`.

---

## 2. Two kinds of data

The schema contains two clearly separated kinds of records.

### Replaceable cache (safe to overwrite from API)
- `sets`
- `cards`
- API price cache (lives inside `cards`)

These can be wiped and re-synced from pokemontcg.io without losing user information.

### Permanent user data (sacred, never overwritten by API sync)
- `holdings`
- `lots`
- `lotItems`
- `binders`
- `binderSlots`
- `wishlist`
- `auditLog`
- `settings`

User data is created and modified only by direct user action through the UI or by an explicit, audited operation (such as restoring a backup).

`appMeta` is system metadata generated by the app itself.

---

## 3. Soft delete

Every user-owned record has a `deletedAt: string | null` field (ISO 8601 timestamp). Default: `null`.

- Deleting an entity sets `deletedAt` to the current ISO timestamp. The record is **not** removed.
- The UI hides soft-deleted records by default and offers a "Recently deleted" / "Restore" affordance.
- Restore sets `deletedAt` back to `null`.
- Permanent delete is not allowed in MVP without an explicit, separate approval PR.
- Cache stores (`sets`, `cards`) do **not** have `deletedAt`. They are managed by sync and reset.

---

## 4. Audit log

`auditLog` records important user-data events. Logged actions include at minimum:

`holding_created`, `holding_updated`, `holding_soft_deleted`, `holding_restored`, `binder_created`, `binder_slot_assigned`, `binder_slot_status_changed`, `card_moved_to_binder_slot`, `lot_created`, `lot_allocated`, `wishlist_item_created`, `manual_value_changed`, `backup_exported`, `backup_restored`, `schema_migration`, `sync_run`, `sync_failed`.

Each entry stores `{ id, action, entityType, entityId, message, createdAt }`. Audit entries themselves are never modified. (They are part of the backup, but they are not editable through the UI.)

---

## 5. Schema versioning and migrations

- Schema version is stored in `appMeta` under the key `schemaVersion`. PR 3 lands `schemaVersion = 1`.
- Dexie's version chain is the single source of truth for upgrades.
- Migration rules:
  1. Adding a new store or a new field is a minor migration. The new field is filled with a sensible default (`null`, `[]`, `0`).
  2. Renaming a field requires a migration that populates the new field from the old one and then deletes the old field.
  3. Removing a field from a user-owned store requires explicit approval; the migration must back up the field's contents into `appMeta` first.
  4. Changing the type of an existing field requires a migration that converts every record.
- Every migration is covered by a Vitest test that opens an old-version database and asserts the new shape.
- `appMeta.lastMigrationAt` is updated on every successful migration.

## 7. TypeScript types — record shapes

Field-by-field reference. Optional fields are marked with `?`. Anything that is `null`-able is typed as `| null`.

### `SetRecord` (cache)

```ts

  name: string;
```

## 8. Relationships

```
sets (1) ────< cards (N)
cards (1) ────< holdings (N)
cards (1) ────< binderSlots (targetCardId, N)
cards (1) ────< wishlist (N)
cards (1) ────< lotItems (N)

lots (1) ────< lotItems (N)
lots (1) ────< holdings (lotId, N)

binders (1) ────< binderSlots (binderId, N)

holdings (1) ────< binderSlots (holdingId, 0..1 — a holding can fill at most one slot per binder)
```

Notes:
- All foreign keys are stored as scalar IDs. Dexie does not enforce referential integrity; the repositories do.
- A cascade soft-delete from a binder soft-deletes its slots. A cascade restore restores them.
- Soft-deleting a holding does **not** soft-delete the lot it belongs to. The lot persists; the slot referencing the holding flips its `status` to `missing` and clears `holdingId`.

---

## 9. Indexing principles

- Filters that appear in the UI must be backed by IndexedDB indexes. Filtering 20 000+ cards in JavaScript is not acceptable.
- Multi-entry indexes (e.g. `*tags`) are used for array-valued fields.
- Composite indexes are used where ordering matters (e.g. `[binderId+pageNumber+slotNumber]` for paging through a binder).

---

## 10. Defaults and validators

`src/domain/validators.ts` enforces the following before any record is written:

- `quantity >= 1`
- `grade ∈ [1.0, 10.0]` when `conditionType === 'graded'`
- If `conditionType === 'raw'`, `rawCondition` is required.
- If `conditionType === 'graded'`, `gradingCompany` and `grade` are required.
- `purchasePrice`, `estimatedValue`, `targetPrice` cannot be negative.
- `pageNumber >= 1`, `slotNumber >= 1`, `slotNumber <= slotsPerPage`.
- `slotsPerPage ∈ {9, 18}`.

Validators run inside repository methods. The UI also surfaces these errors at form-submit time.

---

## 11. ID generation

- All `Uuid` values are generated with `crypto.randomUUID()`.
- IDs are never reused. A soft-deleted record keeps its ID.

---

## 12. Time

- All timestamps are ISO 8601 strings in UTC.
- `Date` objects are not stored. The repositories convert to/from ISO strings at the edges.
